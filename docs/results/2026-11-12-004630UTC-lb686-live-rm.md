- **The 1,136-event gap (00:57:54) is the one loss seen on ebpf2201.** In that second the NIC got 298,050 packets and IP took in 298,216 (`Ip.InReceives`), but only 275,140 were counted as UDP datagrams: 23,076 packets (≈ 1,180 events at ~19.5 packets each) vanished between IP and UDP, with no counter for them (`Ip.InDiscards`, `Udp.NoPorts`, `Udp.InErrors`, `Udp.RcvbufErrors`, softnet drops all +0). The seconds before and after match exactly. Why the kernel dropped them without counting is open; IP reassembly counters (`ReasmFails`) and `nstat` were not sampled.
- **The other ~120,780 missing numbers never reached ebpf2201:** in those minutes the NIC and UDP counts agree to the packet and no drop counter moved. They were lost, or never sent, upstream of the receiver: in the sender, the network or the LB. The pattern (single numbers, often every other one, in bursts of a few minutes) points at the sender side. Only one of the two senders that were registered at the start was still registered at the end.
- Over the whole run, the only drop counter that moved is `rx_steer_missed_packets` (+1,359), background multicast, as on earlier runs.

## The reader: the bottleneck

| | |
|---|---|
| Files | 1,126 of 2 s (the last one 0.6 s), 30,500 events and ~750 MiB each |
| Time per file | mean 3.48 s, p50 3.43, p90 3.76, p99 3.90, max 63.3 s (one file) |
| Throughput | 829.6 GiB in 3,930 s, **1.81 Gbps**, against 3.17 Gbps written |
| Lag (wall clock − file's second) | 5 s at the first file, 107 s after 100 files, 496 s after 400, 1,131 s after 800, 1,672 s at the last |

The reader falls behind by ~0.74 s per 2 s file from the first file on: it is busy all the time (the sum of its write times, 3,916 s, is its whole run). DAOS therefore kept growing for the whole run instead of holding ~20 s, and the reader needed 28 min after the sender stopped to empty it. In an earlier run of the same evening a 5 s reader took 7.6 s per file: the same ~1.8 Gbps, so the file interval doesn't matter. Speeding the reader up (more reads in flight, writing files in parallel, or several readers on a run) is the open item for runs above ~1.8 Gbps.

### Space on the reader node

The reader writes everything it reads to `/scratch/epsdaq`, ~13 GB per minute while busy. When the sender stopped, 13.8M events (~340 GiB) were still only in DAOS and ebpf2203 had 232 GB free with `--min-free 50`, so the reader would have paused. At the user's request the **317 oldest files (250.4 GB, seconds 1794444390–1794445022 = 00:46:30–00:57:02 UTC) were deleted**; their names and sizes are in `deleted_oldest_files.txt` in the run's log folder, and the manifest still lists them. The reader then finished. Kept: 809 files, 598 GB.

## Size in DAOS: `--live-rm` against `--live`

| | This run, `--live-rm` | The same run with `--live` |
|---|---|---|
| Container at the end | empty, destroyed by the reader | **890.8 GB (829.6 GiB)**, 34.2M events, kept |
| Most in DAOS at once | 380.1 GB (354 GiB), only because the reader fell 15 min behind. A reader that keeps up holds `--rm-after` × `--interval` = 20 s plus its own lag: ~8–10 GB | 890.8 GB, growing for as long as the run lasts |
| Growth | — | 377.6 MiB/s = **1.43 TB per hour**, 34 TB per day at 3.17 Gbps |

- With `--live`, sc-demo's 12 TB of NVMe would fill after ~8 h of data at this rate. The run before this one, `e2sar_lb686_1794441647`, was read with `--live` and held 19.7M events, 501 GB, for 21.6 min: the same rate. Its container was destroyed on 2026-11-13.
- The reader's files are the same size in both modes (`--live-rm` changes only DAOS): ~1.43 TB per hour of data on the reader node, so one ebpf node's 894 GB `/scratch` holds ~38 min.
- Space beyond the event bytes is small: the index costs ~235 bytes per batch, ~1.3 GB for this run (0.15%). SCM free went from 209 GB during the run to 215 GB after it.
- The pool's own numbers are rounded to whole TB and freed lazily (`reclaim` lazy): during the run each target had 338 GB of NVMe free, after it 366 GB. They can't be used to measure one container's size.

## Open items

1. The reader's speed (~1.8 Gbps) is below the data rate; see above.
2. 23,076 packets taken in at IP but not counted as UDP at 00:57:54 on ebpf2201: sample `nstat` (IP reassembly, `UdpLite`, `Ip.InDelivers`) in `e2sar_nicmon.sh` to place the next one.
3. Event-number bursts upstream of the receiver: compare with the sender side's logs, and with when 198.124.49.31 left the LB.
4. The sender splits events into ~1.3 KB packets although the receiver's port has MTU 9000; larger packets would cut the packet rate (~295k/s here) by ~6×.
