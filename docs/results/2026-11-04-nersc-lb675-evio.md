# EVIO frames from NERSC through LB 675 to two receivers (2026-11-04)

The first run with a remote sender at NERSC and two receivers on the ebpf testbed writing one DAOS container, with the live reader, the DAOS monitor and the EVIO live viewer on ebpf2203. E2SAR 0.4.0rc1, pool `sc26`, `main` at f2026d8. The sender side is not ours: its command and settings are not known here.

## Setup

LB 675 was reserved for this run on the beta control plane (`ejfat-lb.es.net:18008`) with the admin token from the private `~/.bashrc` (`lbadm --reserve -l xmei-e2sar -d 168:00:00`, FPGA slot 1), with no registered senders: the sender registered its own address, 128.55.83.139 (NERSC).

| Role | Node | Command |
|---|---|---|
| Receiver A (writer slot 0) | ebpf2201 | `e2sar_daos_recv -c --ip 129.57.178.85 --port 20700 --threads 4 --deq 16 --pool sc26 --cont-name e2sar_lb675_1793817098 --report 10 --log-idle` |
| Receiver B (writer slot 1) | ebpf2203 | the same with `--ip 129.57.178.86`, started 10 s later |
| Reader | ebpf2203 | `e2sar_daos_read --pool sc26 --cont e2sar_lb675_1793817098 -o /scratch/$USER/live_e2sar_lb675_1793817098 --live` (5 s files) |
| Monitor | ebpf2203 | `e2sar_daos_monitor` + `viz/daos_monitor/serve.py` (port 8766) |
| EVIO viewer | ebpf2203 | evio-interactive-view `serve.py --live <reader dir> --no-browser` (port 8765) |

Both pages were forwarded to a laptop as in [live-monitoring](../howto/live-monitoring.md). The LB gave each receiver 256 of its 512 slots.

| Event size | 204 to 656 bytes, p50 204, p99 224, mean 206.7. Each event is one EVIO v6 record holding one time frame (bank `0xff60`) |

| Receivers | Lost in reassembly 0, in enqueue 0, failed DAOS operations 0 |
| Receive → commit latency | p50 4.2 ms, p90 6.3, p99 6.3, max 67 ms; `daos_array_write` p50 0.074 ms. The time is batching (3.5 events per batch, `--flush-us 5000`), not DAOS |
| Reader | 615 files of ~15 MiB (~76,300 events each), each written in ~0.8 s. 0 duplicates, strict order inside each file, 47,966 late (an event in a later file than higher-numbered ones) |
| Missing | **1,690 events (0.0036%)** |

The receiver numbers say nothing about lost packets here: an event of ~207 bytes is one packet, so a dropped packet removes the whole event and never counts as reassembly loss. It only shows as a gap in `<run>_missing.txt`.

## The missing events come in 3 bursts

All 1,690 missing events are in 3 of the 615 files, about 13 to 16 minutes apart; the other 612 files have no gaps:

| File (UTC) | Missing |
|---|---|
| 18:57:50 | 581 |
| 19:11:25 | 584 |
| 19:27:55 | 525 |

Inside a burst the gaps are short and close together: 874 gaps, 466 of 1 event, 215 of 2, the rest 3 to 9, usually 2 to 4 event numbers apart. In the 10 s receiver reports around each burst one receiver's rate dips by 60 to 90 events/s, about the size of the burst: A at 18:57:52, B at 19:11:31, A at 19:28:03. The normal jitter is ±50 events/s, so this hints that each burst hit one receiver's path, but doesn't prove it.

Where they were lost is open:

| Counter | ebpf2201 | ebpf2203 |
|---|---|---|
| `rx_discards_phy`, `rx_out_of_buffer` (`ethtool -S enp1s0f1np1`) | 1,103,804 and 0 at 16:48 UTC and after the run: **no NIC drops** | read only after the run (1,079,655 and 2,939,161): unknown |
| `RcvbufErrors` (`/proc/net/snmp`) | 729,645 since boot (2026-10-16), no reading before the run: unknown | 9,586,307 since boot, unknown |

The nightly iperf3 logs keep only per-second differences, so they give no earlier reading. Possible places: the WAN path or the sender (the spacing could be something periodic there), ebpf2203's NIC, or a socket buffer on either node.

## LB 653 before: no data at all

Earlier the same day ebpf2201 was registered for 1 h 20 min on LB 653 (also beta, 21 JLab and NERSC senders) and received nothing: 0 UDP datagrams (`nstat`), while 50 test events of 1 MB sent with `e2sar_perf -s -c` from ebpf2203 through LB 653 all arrived. So that LB and path worked, and no sender data reached it. Its `predictedeventnum` is not a sign of a live sender: it follows the clock in microseconds only while a worker is registered, freezes when the last worker leaves, and is 0 on an LB that never had one.

## One EVIO file from the bundles

The `--live` files are bare EVIO v6 records, without a file header, so `bin/evio_concat.py` (which expects a header in each input) can't join them. The run was joined into one 9.7 GB EVIO v6 file by writing a 14-word file header (`EVIO`, header length 14, the record count, version 6, magic `0xC0DA0100`, big endian), appending the files in manifest order, then `evio_concat.py --fix-last-bit`. The result has 46,850,768 records, the manifest's count; the 56-byte header is the only difference in size. evio-interactive-view needs files under 2 GiB, so split it with its `evio_split.py` first.
