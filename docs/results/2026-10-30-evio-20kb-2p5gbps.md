# 20 KB EVIO events at 2.5 Gbps, with a `--live-rm` reader (2026-10-30)

The [receiver tuning](2026-10-29-receiver-tuning.md) scenario a (20 KB events at 2.5 Gbps, the size coda-fb is expected to send), now with real EVIO frames and the whole streaming chain: sender, receiver, live reader and monitor. One run, node to node on the ebpf testbed, E2SAR 0.4.0rc1, pool `sc26`.

## Setup

The steps of the [walkthrough](../howto/streaming-walkthrough.md), with:

| Role | Node | Command |
|---|---|---|
| Sender | ebpf2201 | `e2sar_evio_send --port-per-segmenter --mtu 9000 -P 4 -s 1 -f 50 -n 240000 -F frames_thread0_file0020.evio -r 2.5 --digests …` |
| Receiver | ebpf2203 | `e2sar_daos_recv --threads 4 --deq 2 --timeout 10000 -b 1073741824 --report 5` (`--inflight 128`, `--flush-us 5000`: the defaults) |
| Reader | ebpf2201 | `e2sar_daos_read --live-rm --interval 2 --rm-after 2 --end-wait 5`, into `/scratch` |
| Monitor | ebpf2201 | `e2sar_daos_monitor` (no page) |

The file's 4,362,277 frames (mean 407 bytes) make 87,246 distinct events of 50 frames, mean 20,360 bytes. Each of the 4 Segmenters sent 240,000 of them, so the file about 2.75 times over.

## Results

| | |
|---|---|
| Sent | 960,000 events, 19.54 GB in 62.5 s: 2.50 Gbps, 15,350 events/s, 0 errors |
| Receiver | 960,000 reassembled and committed. Lost in reassembly 0, in enqueue 0, failed DAOS operations 0 |
| Receive → commit latency | p50 3.1 ms, p90 5.2, p99 6.3, max 29 ms. 40.7 events per batch; `daos_array_write` p50 0.72 ms |
| Reader | 32 files of ~596 MiB (~30,700 events each). 0 missing, 0 duplicates, 41 late |
| Check | `e2sar_live_check.py`: all 960,000 events match their 50 frames of the file, byte for byte. **PASS** |
| Monitor | 960,000 in, 960,000 out, 0 missing; exited when the container was destroyed |

The receiver numbers match scenario a of the tuning (p50 2.4–3.1 ms at `--deq 1–2`), now with real frames.

## The reader is the limit at this rate

Each 2 s bundle took the reader 2.11–2.14 s to write (~280 MiB/s). Its lag behind the data grew during the run: the bundle of the window ending at 814 s was written 3.3 s after it, the one ending at 828 s 4.5 s after, the one ending at 848 s 6.1 s after, about 1 s more every 15 s. A 62 s run is too short for that to matter, and the reader caught up after the sender stopped. A long run at 2.5 Gbps would fall further behind, and with `--live-rm` the data waiting in DAOS would grow with the lag.

Not yet known: whether the time goes to reading from DAOS or to writing `/scratch`. The viewer is not affected, since it reads at most its sample (default 32 MiB) of each bundle.
