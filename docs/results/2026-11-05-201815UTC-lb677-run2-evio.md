# LB 677 run 2: EVIO time frames from NERSC, losses and stopping a receiver (2026-11-05 20:18:15–20:55:35 UTC)

The second run with data on LB 677, container `e2sar_lb677_1793909535`, started right after [run 1](2026-11-05-194730UTC-lb677-run1-evio.md) with the same setup: receivers on ebpf2201 (writer slot 0) and ebpf2203 (slot 1), the `--live` reader into `/scratch/epsdaq/live_e2sar_lb677_1793909535`, the DAOS monitor and the EVIO viewer on ebpf2203, and the 1 s NIC sampler on both nodes. E2SAR 0.4.0rc1, pool `sc26`, `main` at 68d99f1.

Two things were new. At 20:38:58 the receiver on ebpf2201 was stopped with Ctrl-C, on purpose, and ebpf2203 took the whole stream for the rest of the run. And a third sender, 128.55.83.195 (NERSC), registered on the LB next to 198.124.49.31 and 128.55.83.219.

## The three bursts

### 20:27:50: on the way to ebpf2201, again

Event numbers 36,999,182 to 37,000,407 (~80 ms): 584 missing in 297 short gaps, from both sender sequences (287 odd, 297 even). The writer slots (`e2sar_daos_read --list`) show the same thing as in run 1. In the burst's range ebpf2203 stored 608 events, its usual half, and ebpf2201 only 34; just outside it the split is even (4,373 and 4,402). ebpf2201's 10 s report at 20:28:00 drops by ~650 events and logs its 2 partial events. Its NIC and sockets dropped nothing.

That makes five bursts on the same pattern, every 30 minutes at :27:50 or :57:50 UTC, ~525–584 events each: LB 675 18:57:50 and 19:27:55, run 1 19:57:50, run 2 20:27:50, all on ebpf2201's share. (LB 675's 19:11:25 burst, on ebpf2203, is the exception.) Run 2's data ended at 20:55:35, before the next one was due. Run 1 has the details on why this is upstream of ebpf2201.

### 20:38:55: stopping a receiver lost 7,600 events

Ctrl-C on ebpf2201 at 20:38:58. The receiver exited 1 s later and the LB moved all 512 slots to ebpf2203, which went from 0.64 to 1.27 Gbps. In between, 7,600 of ebpf2201's events were lost: 3,848 gaps over event numbers 47,191,479 to 47,206,876 (~1 s): about half the event numbers in that range, ebpf2201's share, interleaved with the ones ebpf2203 stored.

What ebpf2201 stored is clean: its `done/0` record says received = committed = 9,475,532, failed 0. The loss is in the shutdown order of `e2sar_daos_recv` (`bin/e2sar_daos_recv.cpp` at 68d99f1):

1. Ctrl-C stopped the dequeue threads, which finished what they held.
2. Only then did it deregister from the LB and stop E2SAR's receive threads.

| ebpf2201 at stop | Events |
|---|---|
| Reassembled by E2SAR | 9,477,568 |
| Taken from E2SAR's queue and committed | 9,475,532 |
| **Dropped in E2SAR's queue** (step 1 → 2) | **2,036** |
| Sent by the LB after the receiver stopped listening, before the slots moved | ~5,560 |

Run 1's stop, with no data flowing, had reassembled = received (8,511,950), so the gap only shows when stopping mid-stream. Fixed since: `e2sar_daos_recv` now deregisters first and keeps storing until no event has arrived for `--drain-quiet` ms (2 s), then stops ([Stopping](../reference/e2sar_daos_recv.md#stopping)).

### 20:41:30: on ebpf2203, place not known

With ebpf2203 the only receiver: 1,399 events missing over event numbers 49,523,634 to 49,525,104, in 41 gaps. 40 of them are 1 to 5 events; one is 1,326 events long (~87 ms). Both sender sequences are hit (698 odd). ebpf2203's NIC discards, out-of-buffer, UDP `RcvbufErrors`, `InErrors` and `NoPorts`, and the IP and softnet drop counters didn't move. No XDP program is attached. The conntrack table was far from full (35 of 262,144 entries now, 0 drops since boot) and the kernel log has no drop messages.

The NIC sampler shows one odd second:

| ebpf2203, second (UTC) | NIC packets (`rx_packets_phy`) | UDP datagrams (`InDatagrams`) | Difference |
|---|---|---|---|
| 20:41:30 | 110,942 | 110,916 | 26 |
| 20:41:31 | 111,706 | 111,240 | 466 |
| **20:41:32** | **116,259** | **105,498** | **10,761** |
| 20:41:33 | 112,561 | 112,444 | 117 |

10,761 packets is the 1,326-event gap at ~8.1 packets per event. Over the rest of the run the difference is p50 241/s, and no other second goes above 2,680. But the difference isn't only lost UDP: **the data port `enp1s0f1np1` also carries the shared `$HOME` (NFS, port 2049) and SSH**, and the sampler then had no IP or TCP counters to separate them. Two readings fit:

- **Lost inside ebpf2203.** The packets reached the port and no socket. Since boot the NIC's counters add up (packets at the port − packets to the host = discards + out-of-buffer + `rx_steer_missed_packets`, within 120 packets), so a NIC drop would have to be steer-missed (no matching receive rule, e.g. another MAC or IP), which wasn't sampled then. Steer-missed is about the same as the multicast packets received since boot (1,019,566 and 1,029,743), and grew by 0–3/s once sampled, so it is mostly background multicast. A drop after the NIC with no counter, for example by firewalld (active; its counters need root), is the other possibility.
- **Never reached ebpf2203**, like the other bursts, while NFS or SSH traffic filled the second. UDP datagrams that second were 105,498, 6,000–10,500 fewer than the seconds around it (109,000–116,000), about the 10,700 packets of the missing events; and 116,259 packets at the port is ~5,000 above the seconds around it, which other traffic would explain.

The sampler now records `rx_packets` (to the host), `rx_steer_missed_packets`, `Ip.InReceives` / `InDelivers` and `Tcp.InSegs` as well ([`scripts/e2sar_nicmon.sh`](../../scripts/e2sar_nicmon.sh)), which tells the two apart next time.
